## 2. 항목 A·B — 죽은 시간 · 전체 판 길이 (검증 가능)

### 2.1 기대값 (코드에서 산출)

출처: `lib/server/phase.ts:14-25` (`PHASE_DURATION_MS`), `:44-52` (`EARLY_EXIT`), `:58-75` (`nextPhase`).

| 순서 | 페이즈 | 길이 | 조기 종료 | 죽은 시간 성격 |
|---|---|---|---|---|
| 1 | question(1) | 60초 | 사람 전원 제출 시 단축 | 한 문장 쓰는데 60초는 길다(코드 주석 `:17`). **잠재 죽은 시간** |
| 2 | question(2) | 60초 | 사람 전원 제출 시 단축 | 위와 동일 |
| 3 | target | 30초 | **없음(none)** | 1명만 답하고 나머지 대기 = **구조적 죽은 시간 30초 고정**(`:18-20`, §5.3) |
| 4 | chat | 120초 | 없음 | 유일 실시간 구간 — 죽은 시간 아님 |
| 5 | vote | 30초 | 사람 전원 투표 시 단축 | — |
| — | reveal/replay | 무시간 | 조작 전환 | — |

- **전체 판 길이(상한, 아무도 조기 제출 안 함):** 60+60+30+120+30 = **300초 = 5분 00초.**
- **전체 판 길이(하한, 사람들이 즉시 제출):** question1·question2·vote가 즉시 단축 → 대략 **target 30 + chat 120 = 150초 + α.** target·chat은 절대 안 줄어든다.
- **구조적 죽은 시간(최소):** target 30초는 무슨 수를 써도 남는다(조기 종료 없음).

### 2.2 발견 — SPEC과 코드의 판 길이 불일치 (회귀 위험)

**SPEC §5.1과 GAMEPLAY-PLAN ⑥은 `revote`(동점 재투표 20초)를 요구하지만, 코드에는 revote 페이즈가 없다.**

- 근거: `lib/server/phase.ts:66-68` — `nextPhase`가 `vote → reveal`로 바로 간다. `revote` 분기 없음.
- 근거: `PHASE_DURATION_MS`/`EARLY_EXIT`에 `revote` 키 없음(Phase 타입에 있으면 타입 에러가 났어야 함 → 타입에도 없음).
- 근거: `supabase/functions/advance_phase.sql`의 phase 체크·전환에 `revote` 없음(CLAUDE.md/SPEC §18.7 "손대는 순서"에 아직 안 옮김이라 명시).
- **영향:** 동점 판의 실제 길이가 SPEC 기대(+20초, 동점자 한정 재투표)와 다르다. 지금은 동점이어도 곧장 reveal → §18.3의 "동점자 무작위 지목"이 revote 없이 vote 단계에서 처리되는지 별도 확인 필요.

### 2.3 재현 절차 (사람 테스터)

전제: `npm run dev` + 실제 Supabase(`e2e.sh` 환경). 방 하나, 좌석 5(사람 4 + AI 1 예시).

1. 방 생성 → 방장이 lobby에서 시작. **스톱워치 시작(t=0).**
2. question(1) 화면 진입 확인. 아무도 제출하지 말고 대기 → **60초 후** question(2)로 자동 전환되는지, `phase_seq`가 +1 되는지 `/admin`(또는 `GET /api/time`+방 상태)로 확인.
3. question(2)도 대기 → **120초 시점**에 target 진입 확인.
4. target: 지목 대상 1명 외 전원 입력 UI가 잠기는지 확인. **150초 시점**에 chat 진입.
5. chat: **270초 시점**에 vote 진입.
6. vote: 대기 → **300초 시점**에 reveal 진입. **여기서 스톱워치 = 5:00 ±2초여야 Pass.**
7. **죽은 시간 계측:** 3~4단계(target 구간)에서 "대상 외 플레이어가 할 수 있는 행동이 0인 시간"을 별도 스톱워치로 잰다 → **30초 고정**이면 Pass. 대상이 봇인 판과 사람인 판을 각각 3회씩 돌려 **두 경우의 target 길이가 같은지** 대조(§5.3 대칭 검증 — 이게 다르면 즉시 Fail).

### 2.4 조기 종료 경계 케이스

| 케이스 | 기대 | 근거 |
|---|---|---|
| question에서 사람 4명 전원 제출 | 즉시 다음 페이즈(봇은 세지 않음) | I5, `EARLY_EXIT='all-humans'` |
| question에서 3명만 제출, 1명 미제출 | 60초 꽉 채움 | "사람 전원" 미충족 |
| **봇을 사람 수에 잘못 포함해 카운트** | 시작 즉시 전환(버그) → 회귀 감시 대상 | I5 위반 시 증상 |
| target에서 대상(사람)이 즉시 답 | **그래도 30초 채움** | `EARLY_EXIT='none'` — 채워야 Pass |
| vote에서 사람 전원 투표 | 즉시 reveal | `all-humans` |
| 클라 시계를 -5초 조작 후 만료 직전 advance 호출 | 서버가 `advanced:false` 반환, 화면 안 넘어감 | I2, `phase-clock.ts:63` 재무장 |

## 3. 항목 C·D — 릴레이 순서 랜덤성 · 25초 타이머 · 패스 (구현 전, 검증 불가)

### 3.1 왜 지금 검증할 수 없는가 (근거)

`docs/GAMEPLAY-PLAN.md:95-121`의 "④-확장안: 라운드테이블 — 발언권 릴레이"는 문서 스스로 **"CEO 제안을 규칙 안전하게 다듬은 것 … ④⑤를 이걸로 대체하거나 ④ 뒤에 끼워 넣을 수 있다"**라고 적은 *제안*이다. 코드 실측 결과 어디에도 반영돼 있지 않다:

- `lib/server/phase.ts` — `Phase`에 `relay`/`roundtable` 없음. 25_000ms 상수 없음(있는 시간값은 60000/30000/120000뿐).
- `nextPhase` — 발언권을 사람별로 넘기는 상태(현재 발언자 seat, 남은 바퀴 수)가 없음.
- "패스" 동작(§18.5 대칭용) — 봇·사람이 발언권을 넘기는 액션이 스키마·라우트·스토어 어디에도 없음.
- "랜덤 순서" — 발언 순서를 섞는 시드/셔플 로직 없음(`lib/game/rules.ts`의 랜덤은 스파이 선정용 `assignRoles` 하나뿐).

즉 **C·D는 "테스트가 실패"가 아니라 "테스트 대상이 없음"**이다. QA가 지금 Pass/Fail을 매기는 것은 불가능하며, 매긴다면 허위 보고다.

### 3.2 구현되면 이 케이스로 검증한다 (미리 작성한 테스트 설계)

기획안 §④-확장안·`:112-121` 표를 품질 기준으로 환산했다. **구현 착수 시 이 표를 그대로 회귀 스위트에 넣는다.**

| ID | 케이스 | 재현 | 기대(Pass) |
|---|---|---|---|
| R-1 | 발언 순서 랜덤 | 같은 좌석 구성으로 20판 돌려 1번 발언자 seat 분포 수집 | 특정 seat 편향 없음(카이제곱 p>0.05). **좌석 번호순/입장순과 상관 0** — 순서가 정체를 흘리면 Fail(I1) |
| R-2 | 25초 슬롯 | 발언권 받은 자리의 카운트다운 계측 | 서버 시각 기준 25초. 봇 대상·사람 대상 **동일**(§5.3 대칭) |
| R-3 | 패스 대칭 | 봇/사람 각각 패스했을 때 슬롯 처리 | 패스해도 슬롯 시간·다음 전환이 **정체와 무관하게 동일**. 봇만 못 패스하면 Fail(`:118`) |
| R-4 | 봇 주제 응답 | 주제 창에서 봇 무응답 빈도 | **0%** — 봇은 주제에 100% 답한다 (2026-08-08 §18.5 되돌림). 주제만 거르고 대꾸는 하는 자리가 생기면 → Fail |
| R-5 | 한 줄 반응 허용 | 발언 중 타인 이모지/한 줄 입력 | 허용되되 발언권과 무관. 죽은 시간 감소 확인(`:117`) |
| R-6 | 판 길이 상한 | 8인 방 바퀴 수 계측 | 인원 비례 1~2바퀴, 8인×3바퀴(12분+) 방지(`:119`). 릴레이+chat 합계가 상한 이내 |
| R-7 | 랜덤 순수성(I3) | 순서 셔플 로직 위치 확인 | 셔플 시드는 `lib/game/`에 **인자로** 주입(I3 — `Date.now()`/랜덤 내부 사용 금지). 서버가 시드 생성 |

### 3.3 CEO 결정 의존 (기획안이 명시)

`GAMEPLAY-PLAN.md:174-182`는 3D 월드 연결 방향(A 순수 라운지 / B 3D 무대 / C 완전 통합)을 **"임의로 정할 수 없다. CEO 결정이 필요하다"**고 못박았고, 릴레이가 ④⑤를 대체하는지/끼는지도 미확정이다. **C·D 구현 착수 자체가 이 결정에 걸려 있다.**

## 4. 항목 E — 봇/사람 구분 불가 (부분 검증 가능)

봇을 특정할 수 있는 **6개 누수 벡터**를 하나씩 검증한다.

### 4.1 구현되어 검증 가능한 벡터

| V | 누수 벡터 | 방어 장치 | 재현 절차 | Pass 기준 |
|---|---|---|---|---|
| V1 | `public_players` 뷰 컬럼 누수 | 뷰가 `is_bot`/`user_id`/`created_at`을 안 내림(I1, `schema.sql:172-186`) | anon 키로 `select * from public_players` → 컬럼 나열. 브라우저 devtools 응답 확인 | **컬럼 정확히 9개**, `is_bot`·`user_id`·`created_at` 부재. `user_id is null`로 봇 명단 못 뽑음. (`supabase/checks.sh`가 이 검사를 가짐) |
| V2 | 답변 도착 시각 | 봇 답 `visible_at` 미래 박기 + **Broadcast 미사용, 1.5초 폴링**(§6.1, `schema.sql:331-347`) | chat 아닌 페이즈에서 devtools Network/WS 관찰. 답변이 insert 즉시 오는지 | 답변은 페이즈 종료 후 공개. `visible_at` 미래 행이 조기 전달되지 않아야 함. `visible_at` default now() 없음(`:347`) 확인 |
| V3 | target 조기 종료 | 조기 종료 없음(§5.3, `phase.ts:47`) | §2.3의 7단계(봇 대상 vs 사람 대상 각 3판) | target 길이가 **항상 30초** — 정체 무관 |
| V4 | 채팅 반복 문구 | 방에서 안 나온 줄만 선택(I1, `chat.sql:75-92`) | chat 120초 풀 관찰 | 같은 문장 반복하는 자리 없음. 봇 쿨다운 8초(`chat.sql:42`) |
| V5 | 답변/이유 중복 | 봇끼리 겹치지 않게 배정(§17.2) | 봇 2대 이상 방에서 question 답 비교 | 봇 답이 서로 다름 |
| V6 | 봇 투표 결과 반영 | 봇 표는 점수에 안 셈(§8.1, `rules.ts:37-56,99-104`) | reveal 점수 확인 | 봇 표가 스코어·"가장 의심받은 사람"에 영향 없음 |

### 4.2 미구현이라 **현재 봇이 갈릴 수 있는** 벡터 (회귀/결함 보고)

**§18.5의 대칭 장치 2개가 코드에 없다. 이게 E의 최대 리스크다.**

1. **봇 15% 답 거르기(§18.5, SPEC:402) — 티켓 철회 (2026-08-08).** 월드에는 한 번 들어갔다가 되돌렸다. 거른 봇도 사람 말에는 대꾸해서 "주제만 골라 씹는 자리"가 새 표식이 됐기 때문이다. 아래는 철회 전 기록이다.
   - 실측: 답 생성 경로(`supabase/functions/advance_phase.sql` question/target 진입 훅, `lib/agent/prefill.ts`)에 "15% 확률로 답을 건너뛴다"는 분기가 없다. 코드에서 `0.15`는 `lib/agent/disguise.ts:64`의 **오타율(typoRate)**뿐, 답 거르기가 아니다.
   - 증상: 봇이 **항상** 답한다 → 빈 답은 사람만 만든다 → **"답이 빈 자리 = 사람" 확정 신호.** SPEC이 §5.3→§18.5로 두 번 고친 함정 그대로 노출.
   - Pass 기준(구현 후): question·target 각각에서 봇 무응답률 ≈15%, 사람 무응답과 구분 불가.

2. **봇 자발 발화(침묵 8~15초 임계, §18.5, SPEC:412) 미구현.**
   - 실측: `chat.sql`의 `bot_reply`는 **사람 메시지 insert에 반응만** 한다(`send_message`가 호출, `:135`). 아무도 말 안 할 때 봇이 먼저 말 꺼내는 스케줄러가 게임 경로에 없다(월드 워커 `worker/src/bots.ts`의 companion 모드에만 자발 발화 존재).
   - 증상: chat에서 사람이 침묵하면 봇도 침묵 → **"반응만 하는 자리 = 봇"** 신호. SPEC:412가 경고한 바로 그것.
   - Pass 기준(구현 후): 봇마다 8~15초의 **서로 다른** 침묵 임계, 임계 후 봇 1대가 선발화. 임계가 봇끼리 같으면 그 간격이 신호 → Fail.

### 4.3 봇/사람 구분 불가 — 통합 판정 시나리오

**시나리오 QA-E (적대적 관찰자 테스트):** 테스터 1명을 "AI를 특정하려는 시민"으로 두고 한 판을 끝까지 관찰하며 아래를 모으게 한다. 하나라도 봇을 100% 특정하면 **Fail.**

1. devtools로 `public_players` 응답 캡처 → 봇 표식 있나(V1).
2. 답변 공개 시 도착 순서/시각 로그(V2, V3).
3. chat에서 "항상 반응 없음/항상 반응 있음/반복 문구" 자리 찾기(V4, **4.2-2 리스크**).
4. question에서 "빈 답이 절대 없는 자리" 찾기(**4.2-1 리스크**).
5. 판별 근거를 적게 하고, **근거가 규칙상 봇 특정으로 이어지면 결함**으로 티켓.
