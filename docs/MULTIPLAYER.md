# 3D 멀티플레이 — 구조와 작업 순서

`/world` 에서 **같은 방 사람들이 한 3D 공간에 함께 있는** 부분. 게임 규칙(페이즈·투표·정체)은
여기 없다 — 그건 `docs/SPEC.md` 와 Supabase 가 맡는다. 이 문서는 **같이 있는 것**만 다룬다.

```
브라우저 A ─┐
브라우저 B ─┼─ WebSocket ─→ Worker(라우팅) ─→ RoomDO("<room_id>")   ← 방 하나 = 인스턴스 하나
브라우저 C ─┘                                     ├ 사람 소켓 N개  (좌표는 소켓 attachment)
                                                  └ 봇 아바타 M기 (서버가 100ms로 조종)
        │
        └─ 입장 티켓만 Next(같은 오리진)에서 받는다 ─→ /api/world/ticket
```

Supabase 는 **한 줄도 건드리지 않았다.** 스키마·RLS·Realtime 그대로다.

---

## 0. 왜 이 구조인가 — 결정 세 가지

### 결정 1. 별도 서버를 둔다 (SPEC §11의 의도적 예외)

SPEC 은 "별도 WebSocket 서버를 쓰지 않는다"고 못 박았다. 그걸 뒤집은 이유는 하나다.

**빈자리를 채우는 봇 아바타를 누군가의 브라우저가 대신 움직이면, 그 브라우저는 누가 봇인지 안다.**
호스트 한 명이 정답을 들고 게임하는 셈이라 게임이 성립하지 않는다 (I1).
Supabase Realtime 은 클라이언트끼리의 릴레이라 이걸 해결할 주체가 없다.

Durable Object 는 "방 하나 = 인스턴스 하나"가 공짜로 나오고, 그 안에서 서버가 봇을 조종한다.
`idFromName(room_id)` 가 같으면 어디서 접속해도 같은 인스턴스로 모이므로 **방 스코프(I10)가
구조적으로 지켜진다** — 다른 방의 이벤트는 애초에 그 인스턴스에 도달하지 않는다.

### 결정 2. 봇 좌표는 사람과 **완전히 같은 스트림**을 탄다

봇 움직임을 "A→B 로 4.2초간 이동" 같은 계획 한 건으로 보내면 대역폭은 아끼지만,
devtools 를 열면 사람(10Hz 샘플 스트림)과 봇(계획 한 줄)이 한눈에 갈린다.
SPEC §6.1 이 도착 시각 누출 때문에 Broadcast 를 버린 것과 **정확히 같은 함정**이다.

그래서 봇도 100ms 마다 한 샘플씩, "변했을 때만 보낸다"는 사람 쪽 규칙까지 그대로 따른다.
그 대가로 시뮬레이션 틱이 필요해졌다 (§4).

### 결정 3. 입장은 **서명 티켓**으로 한다

본인 확인 토큰(`players.token`)은 httpOnly 쿠키다 (SPEC §17.4). 브라우저 JS 가 읽을 수 없으니
WebSocket URL 에 실을 수 없고, 다른 오리진(워커)으로 자동 전송되지도 않는다.

같은 오리진의 `/api/world/ticket` 이 쿠키를 확인하고 **60초짜리 HMAC 티켓**을 내준다.
워커는 서명만 검증하므로 입장할 때 네트워크 왕복이 0회다 — Next 가 잠깐 죽어도 이미 들어온
사람들은 계속 논다.

|---|---|---|

## 3. 좌표가 흐르는 길

### 송신 (10Hz + 변경 시에만)

```
useFrame(매 프레임)
  └ 값이 바뀌었나?  &&  마지막 송신에서 100ms 지났나?
       └ conn.sendMove(x, z, y, heading, anim)
```

`y` 는 **발 높이**다(눈높이가 아니다). 0 이 바닥이고 점프·가구 윗면에서만 >0 이다.
나중에 붙은 필드라 **없으면 0 으로 읽는다** — 구 클라이언트·구 워커를 끊지 않는다.
공중인지는 `y > 0` 으로 판단한다. `AnimState` 에 `'jump'` 를 넣지 않는 이유는
그 목록이 **서버 화이트리스트**라, 값을 늘리면 구 워커가 새 클라의 move 를 통째로
버려서 뛰는 동안 그 사람이 남의 화면에서 얼어붙기 때문이다.

`changed` 검사를 빼면 **가만히 서 있어도** 8인 방에서 초당 80패킷이 낭비된다.

### 서버 (검증 후 릴레이, 본인 제외)

범위(x·z·y)·유한수·애니메이션 화이트리스트만 본다. **좌표를 보정하지 않는다** —
서버가 고치면 클라와 어긋나 고무줄이 된다. 범위 밖이면 그냥 버린다.

`NaN` 하나가 통과하면 그 사람을 보는 **모든** 클라이언트의 보간이 영구히 깨진다.

### 수신 (150ms 지연 보간)

항상 최신 샘플보다 150ms 뒤를 그린다. 그래야 패킷이 한 번 늦어도 보간할 구간이 남는다.
최신 샘플을 바로 그리면 늦는 순간 아바타가 멈췄다 튄다.

**외삽하지 않는다.** 외삽은 멈춘 사람을 벽으로 밀어 넣는다.

### 봇도 가구에 부딪힌다

가구 데이터·판정은 `lib/mp/collide.ts` **하나에만** 있다. 원래 `app/world/warehouse.tsx`
안에 있었는데, 워커는 그 파일을 못 읽는다(three.js·React가 딸려온다). 그대로 두면
**좌표를 만드는 건 서버인데 가구는 클라이언트만 아는** 상태가 되어, 봇이 소파를 뚫고
지나간다. warehouse.tsx 에는 `THREE.Vector3` 를 제자리에서 고쳐 주는 껍데기만 남겼다.

봇에만 다른 점이 셋 있다.

1. **낮은 탁자에도 안 올라선다** (`stepUp = 0`). 사람은 걸어서 올라가고 그때 발 높이가
   탁자 윗면으로 오르는데(`groundHeightAt`), 봇에게 그걸 주면서 `y` 를 안 올리면
   탁자를 뚫고 걷는 그림이 된다. 돌아가게 두는 쪽이 안전하다.
2. **판정은 항상 발 높이 0으로 본다.** 점프 중(`y>0`)에 풀어주면 소파를 뛰어넘고
   그 안에 착지한다 — 봇의 착지 높이는 늘 0이라 가구 안에 서 있게 된다.
3. **밀어냈는데도 가구 안이면 그 자리로 안 간다.** 소파 두 개가 ㄱ 자로 놓인 구석은
   A 에서 밀면 B 안이고 B 에서 밀면 A 안이라 몇 번을 반복해도 안 풀린다(실측).
   들어가지 않는 게 유일한 답이고, 못 가고 서 있으면 막힘 판정이 받아준다.

**막힘 판정이 없으면 충돌만 넣은 게 더 나쁘다.** 봇이 소파 뒤 목적지를 향해 영원히
소파에 비빈다. 몇 초(`STUCK_MS`) 동안 목적지에 가까워지지 못하면 딴 데로 간다 —
사람도 못 가는 데를 계속 밀지 않는다. 목적지 자체도 가구 안은 피해서 뽑는다.
정면으로 눌려 아예 못 갈 때는 더 빨리(`BLOCKED_MS`) 튼다.

**막힘 시계는 걷으려 애쓴 시간만 잰다.** 말하려고 서 있는 동안에도 세면, 3초 치고 나서
가던 목적지를 잊고 방향을 튼다 (테스트가 잡아낸 실제 버그다).

### 걷는 모습이 이상해지는 두 가지

충돌을 넣으면 바로 따라오는 문제다. 둘 다 화면에서 먼저 보인다.

1. **옆걸음·뒷걸음.** 가구를 따라 미끄러지는데 시선은 목적지를 보고 있으면 그렇게 보인다.
   목적지가 아니라 **실제로 간 방향**으로 돈다. 사람은 가는 쪽을 본다.
2. **제자리걸음.** 눌려서 못 가는데 `anim` 이 `walk` 면 발만 구른다.
   못 갔으면 `idle` 로 둔다 — 사람도 부딪히면 멈추고 방향을 튼다.

밀어내기는 **한 번으로 끝나지 않는다**(`MAX_PASSES`). 소파와 낮은 탁자처럼 밀어내기
범위가 맞닿은 가구가 있어서, A 에서 밀려난 자리가 곧 B 안이 된다. 사람 쪽도 같이 좋아졌다.

### 월드 AI 는 게임 좌석이 아니다

`/world` 는 **게임을 시작하지 않아도** AI 가 서 있다. 혼자 들어가도 하나가 걸어다니고
말을 건넨다. 그 AI 는 `players` 행이 **아니다** (`lib/server/world-ai.ts`).

로비에 봇 행을 앉히면 안 되기 때문이다. `public_players` 는 `phase='lobby'` 동안
`is_ready` · `lobby_line` 을 내려주는데, 봇만 그 값이 비어 있으면 **값이 있는 자리 =
사람**이 되어 봇 명단이 통째로 드러난다 (`supabase/policies.sql` 에 같은 경고가 있고,
SPEC §15-3 에 아직 미결정으로 열려 있는 항목이다).

그래서 월드 AI 는 DB 에 없다. 로비 화면 · 투표 · 역할 어디에도 안 나타나고,
`buildWorldRoster` 가 워커에게 줄 명단에만 얹는다. **게임 규칙은 한 줄도 안 바뀐다** —
`phase !== 'lobby'` 가 되면 얹지 않고 진짜 좌석이 그 자리를 대신한다.

id 는 방 id 를 해시해 **진짜 uuid 와 구별되지 않게** 만든다. `world-ai-1` 같은 걸 쓰면
id 모양만 보고 AI 를 골라낼 수 있다 (I1). 결정적이라 DO 가 재시작해도 좌표를 이어받는다.

`agent_logs.player_id` 가 `players(id)` 를 참조하므로 월드 AI 의 발화는 기록하지 않는다
(`/api/agent` 의 `no_log`). 안 그러면 발화마다 외래키 오류가 콘솔을 덮는다.

### 봇이 말할 때 — 예약해 두고 서 있는다

사람은 `Enter` 를 누른 순간 `composing` 이 되고 `keys.current = {}` 로 **발이 묶인다**
(`app/world/world-scene.tsx`). 즉 **사람의 말풍선은 항상 멈춰 선 아바타 위에** 뜬다.
말풍선은 HUD 가 아니라 3D 에 뜨므로(`world-scene.tsx` 의 `Html`), 봇만 걸어가면서
말하면 그 자리가 눈으로 갈린다 — 1분이면 충분하다 (I1).

그래서 봇의 발화는 두 걸음이다.

```
tick ① shouldChat      → scheduleSpeech(문구)   pendingText 가 걸린다
     ② stepBot         → typeAt 이 지났으면 걷지도 새로 뛰지도 않는다 (anim='idle')
     ③ takeSpeech(now) → speakAt 이 지났으면 그때 broadcast
```

말을 꺼내는 길은 두 갈래고, 다른 건 **읽는 시간**뿐이다.

| | 계기 | readDelay |
|---|---|---|
| 자발 | `shouldChat` — 25~75초마다, **단 마지막 발화가 사람 것일 때만** | 0 (읽을 게 없다) |
| 반응 | 사람이 채팅을 보냈다 → `pickResponder` | 0.5~2.5초 |

읽는 시간이 0 이면 **사람이 말한 바로 그 순간 멈추는 아바타**가 생긴다. 그 동시성은
말풍선이 3D 에 뜨므로 눈에 띈다 — 사람은 읽고, 마음먹고, 그제서야 손이 멈춘다.

자발 발화의 조건(`shouldChat` 의 `mayInitiate`, `room-do.ts` 의 `humanSpokeLast`)은
**나중에 붙인 게 아니라 고쳐야 했던 버그**다. 시각만 보고 25~75초마다 말을 꺼내던 때는,
사람이 조용하면 대화 기록이 제 발화로만 채워졌다. 그 상태에서 LLM 은 trigger 없는
`chat` 분기("대화 흐름에 자연스럽게 끼어들어라")를 타므로 **자기가 방금 한 말에 대꾸했다** —
혼자 떠들고 혼자 답하는 아바타가 됐다 (실측). 규칙은 하나다: **누가 받아 주기 전에는
두 번 연달아 말하지 않는다.** 기록이 빈 방의 첫 한마디만 예외다.

`pickResponder` 는 I1 이 두 번 걸리는 자리다.
- **한 사람 말에 봇은 최대 하나만** 반응한다. 둘이 같이 대꾸하면 그 둘이 한 번에 묶인다.
- **확률 게이트는 없다** (`BOT_REACT_CHANCE = 1`). 알맹이 있는 말은 다 받는다.
  아래 「절반을 씹지 않는다」.
- **봇의 말에는 반응하지 않는다.** 호출부가 사람 소켓의 `chat` 에만 있어서 구조적으로
  지켜진다. 봇끼리 주고받기 시작하면 끝없이 돈다.

### 절반을 씹지 않는다 — 확률 게이트를 없앤 이유

`0.45 + 쿨다운 45초` → `20초` → `쿨다운 0 + 인원별 확률(1/H)` → **`1.0`**.
세 번 다 같은 신고에서 밀려났다: **"대화를 안 하니까 AI 같다."**

원래 논리는 "사람은 남 말 절반은 그냥 씹으니, 늘 대꾸하는 자리는 반응률만으로 봇이
된다 (I1)" 였다. 종이 위에서는 맞지만 3D 월드에서 돌려 보면 반대다.

- 사람이 남 말을 씹는 건 **여럿이 동시에 떠들 때**다. 이 방의 AI 는 1대, 좌석은 3~9개다.
  자기한테 온 말을 씹는 자리는 사람이 아니라 **자리를 비운 사람**으로 보이고, 그 자리가
  곧 AI 로 지목된다.
- 씹은 자리는 **대화 기록에 아무것도 안 남긴다.** 판별 근거가 될 발화가 없으니 소거법으로
  갈린다 — 조용한 게 안전한 게 아니다.
- 반응률로 갈리려면 여러 판을 세어 봐야 하지만 **침묵은 한 판에서 바로** 보인다.
  같은 I1 이라도 노출 속도가 다르다.

남은 제동은 확률이 아니라 **구조**다.

| 무엇 | 어디 | 막는 것 |
|---|---|---|
| `hasContent` | `bots.ts` | "ㅋㅋ"·"ㅇㅇ" 처럼 답할 거리가 없는 말 (동문서답 방지) |
| `speechHeld` | `pickResponder` | 이미 한 줄 치는 중인 봇. 사람도 한 번에 한 줄이다 |
| `speechSeq` | `scheduleSpeech` | 여러 줄이 몰아치면 예약이 서로를 덮어써 **마지막 말에만** 답한다 |
| 하나만 고른다 | `pickResponder` | 둘이 같은 말에 대꾸하면 그 둘이 한 번에 묶인다 |
| `topicDue` | 아래 | 주제에 답할 차례를 잡담이 뺏는 것 |

되돌릴 자리는 `BOT_REACT_CHANCE` 하나다. 인원별 계산(`reactChance`)은 **지웠다** —
죽은 공식을 남겨 두면 다음에 고치는 사람이 그게 사는 길인 줄 안다.

### 주제에 답할 빚 — `topicDue`

speak 창에서 봇은 자리를 잡고 LLM 답을 기다린다. 그 사이에 사람이 채팅을 치면 대꾸
예약이 걸리고, 그 예약이 **`speechSeq` 를 올려서** 날아오던 주제 답을 무효로 만든다
(`upgradeSpeech` 의 seq 검사). 화면에는 **주제는 씹고 잡담에만 답하는 자리**가 남는다 —
다 같이 주제에 답하는 45초에 그 자리만. 확률 게이트를 없애 대꾸가 잦아진 만큼 더 자주
걸린다.

```
primeForTopic(speak=true)  → topicDue = 창 마감
   pickResponder            → topicDue 가 남은 봇은 후보에서 뺀다
   botSpoke                 → topicDue = 0   (제때 온 답도, 지각한 답도 여기로 모인다)
```

- 값이 **창의 마감 시각**이라 스스로 만료된다. LLM 이 끝내 안 와도 다음 단계로 안 끌고 간다.
- 침묵하기로 뽑힌 라운드(`BOT_SILENCE_CHANCE`)는 애초에 0 이다 — 할 말이 없는데 대꾸까지
  막으면 그 45초가 통째로 조용해진다.
- 빚을 갚은 뒤에는 **같은 창에서도 평소처럼** 사람 말을 받는다.

### 하드코딩 문구 풀은 없다 — 할 말이 없으면 말하지 않는다

**월드 AI 가 선 방(로비)에는 문구 풀이 없다.** 예전에는 `WORLD_LINES`(18줄)를 줬는데,
그게 곧 **월드에서 들리는 말의 거의 전부**가 됐다 — 몇 분만 있어도 같은 문장이 돌아오고
그 반복이 그대로 봇 표식이었다. 워커 쪽 `FALLBACK_LINES`(8줄)도 같은 이유로 지웠다.
코드로 된 대비책은 반드시 "제일 자주 들리는 말"이 된다. LLM 이 흔들릴 때마다 그쪽으로
떨어지기 때문이다.

지금 풀을 받는 건 **게임이 도는 방**뿐이고(`bot_line_pool.phase='chat'`), 그 방에서는
`pickLine` 이 **최근에 나온 줄을 빼고** 뽑는다 — 풀이 80줄 남짓이라 그냥 뽑으면 토씨까지
같은 말이 금방 또 나온다. 로비 방에서는 `pickLine` 이 `null` 이다.

### LLM 이 자리를 채운다 — 예약해 두고 채워 넣는다

반응은 예약과 **동시에** `/api/internal/world-agent` 를 부른다. 답이 제때 오면
`replaceSpeech` 가 잡아 둔 자리에 문구를 넣는다.

```
사람이 말한다
  ├ scheduleSpeech(null)     typeAt·speakAt 이 여기서 정해지고, 다시 바뀌지 않는다
  └ void upgradeSpeech()      예산 = speakAt 까지 남은 시간
        ├ 제때 왔다 → replaceSpeech(문구)      LLM 반응이 나간다
        └ 늦었다·실패했다 → 아무 일도 없다      말없이 서 있다 간다
```

### 무대는 `synthetic` 이 아니라 **판이 도는가**로 갈린다

워커는 `in_round` 와 `round_topic` 을 같이 보낸다 (`RoundContext`). 오리진은 이걸로
시스템 프롬프트의 무대를 고른다 — 라운지면 `setting:'world'`(WORLD_RULES: "판이
시작되기 전"), 판이 돌면 `setting:'game'`. 그리고 `trigger` 가 `round_topic` 과 같으면
그 차례는 **판이 던진 질문에 답하는 자리**라 `phase:'question'` 으로 넘겨
`[지금 답할 질문]` 틀을 태우고, 되묻기는 끈다.

**이 값 없이는 오리진이 알 수 없다.** 월드의 판은 `rooms.phase` 를 `'lobby'` 로 둔 채
돌아서(`app/api/room/start-world`), `buildWorldRoster` 가 보는 값만으로는 주제가 떠 있는
45초와 라운지 잡담이 똑같아 보인다. 한동안 그래서 **주제가 나와도 AI 가 조용했다** —
"판은 아직 시작 전"이라고 들은 채 주제를 받아 낸 답이 오리진의 거르개(폴백·회피·상한)에
걸려 통째로 버려졌기 때문이다 (신고 2026-08-07).

**`speakAt` 을 건드리지 않는 게 전부다.** 발화 타이밍 분포가 LLM 성공/실패와 무관해야
자리 단위 봇 신호가 안 된다 — `lib/agent/chat-reply.ts` 가 `visible_at` 을 건드리지
않는 것과 같은 규칙이다.

그래서 `speechHeld` 와 `pendingText` 를 **따로 둔다.** 자리를 잡는 순간에는 할 말이
정해져 있지 않고, 끝내 안 정해질 수도 있다. 그래도 **서서 치는 시간은 똑같이 흘러야**
한다 — 둘을 한 필드로 묶으면 LLM 을 기다리는 동안만 발이 안 묶이고, 그 차이가 곧
"기다리는 자리 = 봇"이 된다. 실패했을 때 달라지는 건 말풍선이 안 뜬다는 것 하나뿐이고,
그건 자리가 아니라 LLM 상태에 걸린 차이라 봇을 특정하지 못한다.

**무엇을 답할지도 실어 보낸다.** 반응을 부른 그 한마디를 `question` 으로 넘긴다.
안 넘기면 "대화 흐름에 자연스럽게 한마디 끼어들어라" 분기를 타는데, 월드에서 봇이
입을 여는 계기는 **누가 말을 걸었을 때**라 그건 상황이 아니다 — 흐름에는 맞지만
질문에는 안 맞는 답이 나온다 (실측: `"안녕"` → `"그러게"`). 기록에서는 빼고 넘긴다.
남겨두면 같은 문장이 두 번 나와 `generate.ts` 의 에코 검사가 베끼기로 오인한다.

**치는 시간은 발화 길이와 무관하다** (`BOT_TYPE_CHARS_*`). 원래는 예약된 풀 문구의
길이로 지연을 잡았는데, 그 문구는 LLM 이 오면 통째로 갈아치워지므로 **아무도 못 볼
문장의 길이**가 타이밍을 정하고 있었다 (풀이 사라진 지금은 잡을 길이조차 없다). 게다가 그 지연에 맞추려고 답 길이에 상한을
걸어야 했고, 질문에 제대로 답한 문장이 되레 그 상한에 걸려 버려졌다 (실측 2/3).
지연을 내용과 끊으니 길이가 타이밍으로 새지 않아 I1 도 더 단단해졌다.

예산은 `readDelay`(1.2~4초) + `typingDelayMs`(≈1.4~2초)다. 그 뒤에 온 답은 이미 말한
뒤라 버려지므로 워커는 딱 그만큼만 기다린다(`AbortSignal.timeout`). `BOT_READ_*` 를
줄이면 예산이 같이 줄어 대부분 빈 자리로 떨어진다(= 말없이 지나간다) — 그 상수의
주석에 이유가 있다.

`speechSeq` 는 응답이 **자기가 부탁했던 그 발화**에만 닿게 하는 열쇠다. 기다리는 사이
그 말이 이미 나가고 다음 예약이 걸렸으면 번호가 달라 조용히 버려진다.

워커는 LLM 키도 페르소나 프롬프트도 모른다 (I4). 나가는 건 "이 방의 이 봇이, 이 대화
뒤에 한마디 한다"뿐이고, 조립·호출·길이 컷은 전부 Next 안에서 끝난다.
`/api/agent` 를 거치므로 `agent_logs` 도 그대로 남는다.

길이는 라우트가 두 가지로 잡는다. 둘 다 **실측으로 얻은 규칙이다.**
- **첫 발화만 쓴다.** 2D 는 두 줄을 각자의 지연으로 따로 보내지만(§5.4) 월드의
  말풍선은 하나다. 이어붙이면 길이가 두 배가 되고 그만큼 잘려 나간다.
- **상한을 넘으면 자르지 않고 버린다.** 잘린 말끝("…주말에 일도 많이")은 봇 티가
  확실하게 난다 — 사람은 문장을 하다 말지 않는다. 버리면 그 자리는 말없이 지나가고,
  침묵은 최소한 잘린 문장보다 사람에 가깝다. 이어붙이던 때는 3건 중 2건이 잘렸다.

상한은 지연 오차 안에서 잡는다. `speakAt` 은 **미리 뽑은 글자 수 예산**(`BOT_TYPE_CHARS_*`)
으로 이미 정해졌고 `typingDelayMs` 는 글자당 55ms 라, 그 예산과 상한의 차이는 1초 안이다 —
`readDelay`(1.2~4초)와 지터(1.2초)가 만드는 폭 안에 묻힌다.

### 월드 대화가 헛소리가 되는 세 가지 (전부 실측으로 걸렸다)

셋 다 "LLM 이 안 붙었다"가 아니라 **LLM 이 거의 불리지 않았다**는 문제였다.
사용자가 본 AI 발언 — "그래서 누구 찍을 거야" · "시간 얼마 안 남았지" — 은
한 줄도 빠짐없이 게임 문구 풀이었다.

1. **게임 문구 풀을 쓰고 있었다.** `bot_line_pool.phase='chat'` 은 게임이 돌아가는
   중을 전제한 말들이다. 라운지용 문구(`WORLD_LINES`)로 갈아 끼워 봤지만 이번엔 그
   18줄이 전부가 됐다 — 결국 **풀 자체를 없앴다.** 위의 「하드코딩 문구 풀은 없다」.
2. **게임 페르소나를 쓰고 있었다.** 그쪽은 의심을 받아치고 회사 얘기로 새도록
   만들어져서, 그냥 노는 공간에서는 동문서답이 된다 ("안녕하세요" → "야 근데 야근
   너무 힘들어"). 월드에는 `worldPersonaForSeat` 을 준다.
3. **아껴 말하는 값을 그대로 쓰고 있었다.** 반응률 45% · 쿨다운 45초는 봇이 여럿
   섞인 게임용이다. AI 가 하나뿐인 방에서는 열 번 걸어 네 번 답하고 45초를 잠근다 —
   숨길 게 없는 방인데 그냥 고장 난 것처럼 보인다. `COMPANION_*` 로 가른다.
   (2026-08-07: 게임 쪽 값도 바뀌었다 — 쿨다운도 확률 게이트도 없다.
   위 「절반을 씹지 않는다」.)

**자발 발화에도 LLM 을 붙인다.** 안 붙이면 그 자리는 아무 말도 못 한다(예전에는
평생 풀 문구만 말했다).
그때는 답할 상대가 없으므로 `trigger` 없이 부른다(흐름에 끼어드는 분기).

고친 뒤: 방마다 한마디씩 8번 물어 **8번 다 문맥에 맞는 답**이 나왔다.

서 있는 시간은 `typingDelayMs`(`lib/agent/disguise.ts`) + 지터다. 2D 게임과 **같은
곡선을 import 해서** 쓴다 — 재는 대상이 "사람이 이 길이의 한국어를 치는 데 걸리는
시간"으로 같기 때문이다. 복사해 두면 한쪽만 손봤을 때 월드에서만 티가 나기 시작한다.

**`speakAt` 은 정해진 뒤 바뀌지 않는다.** 나중에 LLM 이 붙으면 `pendingText` 만
갈아끼우고 시각은 그대로 둔다 — 발화 타이밍 분포가 LLM 성공/실패와 무관해야
자리 단위 봇 신호가 안 된다 (`lib/agent/chat-reply.ts` 가 `visible_at` 을 건드리지
않는 것과 같은 규칙).

최근 채팅은 DO 가 메모리로만 들고 있다(`chatLog`, 20줄). 월드 채팅은 저장하지 않으므로
이게 유일한 기록이고, evict 로 날아가도 무해하다 — 비면 "방금 나온 문구 피하기"만
못 할 뿐이다. LLM 이 붙으면(3단계) 여기가 그대로 대화 맥락이 된다.

이 상태 기계는 브라우저로 확인하기 어렵다(자발 발화가 25~75초에 한 번이고 반응은
확률이다). 두 겹으로 잡는다 — 조각은 `tests/worker/bots.test.ts`(`worker/src` 중
유일한 `npm test` 대상), 배선은 `world:smoke` 의 「사람이 말하면 봇이 멈춰 서서 LLM
문구로 대꾸한다」가 본다. 후자는 실제 소켓으로 말을 걸어 보고 세 가지를 한꺼번에
확인한다 — 반응이 오는가 · 발화 직전 `anim` 이 `idle` 이었는가 · 풀 문구가 덮어써졌는가.
LLM 도 Supabase 도 띄우지 않는다. 가짜 Next 가 두 내부 경로를 흉내 낸다.

## 4. 틱 루프에 대하여

DO 에 `setInterval` 을 두면 hibernation 이 깨져 과금이 는다. 그래서 조건을 좁혔다.

- 사람이 **1명 이상** 접속해 있고, 봇이 **1기 이상**일 때만 돈다
- 마지막 사람이 나가면 즉시 멈춘다 → 빈 방은 평소처럼 잠든다
- DO 가 evict 되어 타이머가 날아가도, 30초 알람과 다음 수신 메시지가 되살린다

**알람 슬롯은 하나뿐이다.** 유령 소켓 청소 · 시뮬레이션 복구 · 봇 좌표 저장을 한 핸들러에서
전부 처리하고 다음 알람을 직접 다시 잡는다. 사람이 0명이면 **재예약하지 않는다** —
재예약하면 빈 DO 가 영원히 주기적으로 깨어난다.

하트비트(`ping`/`pong`)는 플랫폼 auto-response 가 받으므로 DO 를 깨우지 않는다.
클라이언트는 JSON 이 아니라 raw 텍스트 `"ping"` 을 보내고, `onmessage` 는 **파싱 전에** 걸러낸다.

## 5. 서버 권위 경계

| 항목 | 권위 | 이유 |
|---|---|---|
| 좌표 · 회전 · 애니메이션 | **클라** (서버는 범위 검증만) | 반응성 우선. 틀려봐야 남의 화면에서 위치가 어긋날 뿐 |
| 좌석 · 닉네임 | **서버** (티켓 서명) | 사칭 방지. 클라가 보낸 값은 보지도 않는다 |
| 채팅 시각 · 순서 | **서버** | 모두가 같은 순서를 본다 |
| 누가 봇인가 | **서버만** | 새면 게임이 즉시 끝난다 (I1) |
| 역할 · 정체 · 페이즈 | **Supabase** | 워커는 알지도 못한다 |

경쟁 랭킹처럼 좌표 치팅이 판돈인 게임이면 좌표도 서버 권위로 올려야 한다.
그 경우 "틱 루프 최소화"가 성립하지 않으므로 DO 대신 상시 프로세스가 맞다.

### 다른 컴퓨터와 같이 할 때

로컬 왕복이 되면 남은 건 **주소 세 개를 전부 공개로 바꾸는 것뿐이다.**
자세한 순서는 `worker/README.md`「다른 컴퓨터와 같이 하기」에 있고, 요점만 적으면:

```
브라우저 → Next    사람들이 여는 주소 (터널 또는 Vercel)
브라우저 → 워커    NEXT_PUBLIC_WORLD_WS_URL — 반드시 wss://
워커   → Next     NEXT_ORIGIN            — 여기서 제일 많이 막힌다
```

마지막 화살표가 함정이다. 배포된 워커는 Cloudflare 엣지에서 도니까 `127.0.0.1`은
그 컴퓨터가 아니다. 그런데 `/health`는 200, 소켓도 열린다 — **워커는 멀쩡한데 방만
비어 보인다.** 그래서 `npm run world:deploy`가 `.env.local`의 `NEXT_ORIGIN`을
`--var`로 실어 보내고, 로컬 주소면 배포 자체를 막는다.

```bash
NEXT_URL=<공개 Next 주소> npm run world:verify   # 밖에서 본 전체 왕복
```

**막히면 ①부터 본다.** ①이 통과하는데 ②가 안 되면 문제는 워커가 아니라
티켓 발급(`/api/world/ticket`)이나 좌석 명단(`/api/internal/world-room`) 쪽이다.

브라우저 두 개로 확인할 때는 **다른 프로필/시크릿 창**을 쓴다.
쿠키를 공유하면 같은 자리로 붙어 서로를 덮어쓴다.

## 7. 새로 손댈 때 주의할 것

1. **`PlayerSnapshot` 에 필드를 더할 때마다 "이걸로 봇을 골라낼 수 있나"를 먼저 묻는다.**
   `joinedAt` 같은 걸 넣으면 봇은 방 생성 시각에 뭉쳐 있어서 전부 특정된다
   (`public_players` 에서 `created_at` 이 샜던 것과 같은 사고 — SPEC §7.2).
2. **양쪽 핸들러를 같은 커밋에서 고친다.** 한쪽만 고치면 런타임에 조용히 깨진다.
3. **`PROTOCOL_VERSION` 은 의미가 바뀔 때만** 올린다. 필드 추가는 전방 호환이다.
   올렸으면 **워커를 클라이언트보다 먼저 배포한다.**
4. **메시지 크기 상한을 하나로 합치지 않는다.** 큰 페이로드가 조용히 드롭되면 원인 찾는 데
   하루가 간다. 상한에 걸려 버릴 때는 로그를 남긴다.
5. **방을 옮길 때 이전 방 상태를 전부 지운다** (`store.reset()`). 안 지우면 새어 나온다.
6. 브로드캐스트는 O(N²)다. 8인 × 10Hz = 초당 약 640 메시지 발신.
   50~100인을 노린다면 관심 영역(AoI) 필터나 배치 전송이 필요하다.

## 8. 아직 안 한 것

- **게임 페이즈와의 연결.** 워커는 페이즈를 모른다. "vote 페이즈에는 다들 앉는다" 같은 연출을
  넣으려면 `/api/internal/world-room` 이 이미 주는 `phase` 를 쓰면 되지만, 그러면 워커가
  게임 규칙을 알기 시작한다 — 넣기 전에 그게 맞는지 한 번 더 생각할 것.
- **월드 채팅과 게임 채팅의 통합.** 지금 월드 채팅은 릴레이만 하고 저장하지 않는다.
  게임의 대화 기록은 Supabase `messages` 가 따로 갖는다 (SPEC §6.1).
- **아바타 외형.** 캡슐 + 구다. `mask_id` 는 프로토콜에 이미 실려 있으니 모델만 갈아끼우면 된다.
- **재접속.** 끊기면 다시 입장 화면으로 간다. 자동 재접속은 티켓을 다시 받아야 한다(60초 만료).
